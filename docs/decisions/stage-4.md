# Stage 4 decision log: Viva session, typed only

- **A viva's state lives in its `sessions` row, not in the API or the browser.** `state`, `current_position` and `ends_at` say exactly where a student is, so a refresh, a dropped connection or a second copy of the API all carry on from the same place. Nothing on the server runs a timer: a session past its deadline is completed the next time anyone touches it, and closing the exam completes the rest. Rejected: keeping sessions in API memory or timing them with background tasks, which a restart loses and which ties each student to one server process.
- **The session is a forward-only state machine enforced by the API under a row lock.** `joined -> in_progress -> completed`, and an answer is accepted only for `current_position`: no going back, no skipping ahead. Each change runs after `SELECT ... FOR UPDATE` on the session, so two requests for one session run one after the other. The browser can still only read (stage 1), so the rules cannot be skipped by writing to the database directly. An answer sent within 20 seconds after the deadline is still saved, because the page sends what was typed when the clock reaches zero.
- **Submits are idempotent: the page makes one key per question and sends the same key on every retry.** Under the row lock, the API finds an answer already saved with that key and returns the session as it stands instead of saving again. The unique constraints on `answers` are the backstop. Hints work the same way: the request names which hint it wants (first or second), so a double click costs one hint. Hints are counted on `session_questions` the moment they are shown, so a refresh cannot erase one.
- **Each student gets one approved question per slot of the exam's mix, from the experiment they performed.** The mix is copied into the exam's config when it is created, so a later change to the subject cannot give two students different mixes. Within a slot, the question given out least often in this exam is chosen, at random among ties. The whole join, session and draw, is one transaction. An exam cannot open until every slot of every chosen experiment has an approved question. Rejected: assigning experiments at random, because the viva and the own-code question in stage 8 must be about the program the student actually wrote.
- **Open: a student whose machine fails cannot rejoin from another browser yet.** `unique (exam_id, roll_number)` refuses a second login with the same roll number, which stops anyone taking over someone else's viva, but there is no teacher action yet to hand a session to a new login. To add before the pilot.
